# Редизайн страницы проекта

## Контекст

Сейчас страница проекта (`ProjectDetailPage`, `src/pages/resources.jsx:899`) — это одна колонка: `DetailHeader` (название + описание + чипы) и линейный стек секций (Задачи, Проблемы, Команда, Цели, Внешние ссылки) внутри `DetailLayout` с боковой колонкой (Статус/Ключ/Участники/кнопка загрузки, только для чтения кроме кнопки). Редактирование названия/описания/статуса идёт через модальный диалог `ProjectCrudDialog`, вызываемый кнопкой «Редактировать».

Задача — переработать эту страницу по образцу уже существующих шаблонов (`TaskDetailPage`, `pages/tasks.jsx:480`; `PersonDetailPage`, `pages/resources.jsx:608`): вкладки, инлайн-редактирование, меню «⋯» с архивом/историей версий/удалением вместо диалога.

## Цели

- Вкладки верхнего уровня: **Описание**, **Контекст**.
- Внутри «Контекст» — подвкладки: **Команда** (с управлением загрузкой через кнопку в «Свойствах», не в самом списке), **Задачи** (только активные, отсортированные), **Проблемы** (только нерешённые), **Ссылки**, **Заметки** (новый раздел, ранее отсутствовал).
- Постоянная вторая колонка **«Свойства»**: Статус (иконка + текст, редактируется по клику), Ключ (редактируется по клику), кнопка «Управлять загрузкой».
- Кнопка «Редактировать» заменяется на меню «⋯»: Архивировать/Восстановить, История версий, Удалить — по аналогии с задачами.
- Название, описание и статус редактируются инлайн, без диалога (как у задачи). Диалог редактирования проекта убирается; диалог создания проекта остаётся.
- Раздел «Цели» с проектной страницы убирается.
- У проектов появляется полноценный архив (`archivedAt`), как у задач: архивные проекты не показываются в общих списках/пикерах/расчётах загрузки, но остаются доступны по прямой ссылке для восстановления.

## Не входит в объём

- Отдельная страница/фильтр «Архивные проекты» в списке `ProjectsPage` — не создаётся. Восстановление архивного проекта возможно только с его собственной страницы (по прямой ссылке), как и у архивных задач.
- Любые изменения модели данных проекта, кроме `archivedAt`.
- Изменения `/api/projects/:id/detail` (набор полей ответа не меняется).

## Layout

Хедер: кнопка "← Проекты" слева, меню «⋯» справа. Ниже — инлайн-редактируемое название (аналог `TaskTitleEditor`: `MentionEditor` в режиме `singleLine`, сохранение по blur). Никаких чипов статуса/участников в хедере — статус переезжает в «Свойства».

Дальше — верхнеуровневые `Tabs` (`components/patterns.jsx:15`) "Описание"/"Контекст" внутри `DetailLayout` (`entity-detail-main`), справа — `aside` с полями «Свойства» (без изменений структуры `DetailLayout`, только содержимое `aside` и `children`).

```
[← Проекты]                                          [⋯]
[Название — инлайн]

[Описание] [Контекст]                      | Свойства
------------------------------------------ | Статус: ⬤ Активен
  ...контент активной вкладки верхнего...   | Ключ: KODE
  уровня...                                 | [Управлять загрузкой]
```

## Вкладка «Описание»

Только описание проекта, инлайн-редактируемое `MentionEditor` (`onChange`/`onBlur`, паттерн `TaskDetailPage`, `tasks.jsx:620`), с упоминаниями людей/проектов и плейсхолдером "Добавить описание…".

## Вкладка «Контекст»

Внутри — второй уровень `Tabs` (тот же компонент) с локальным состоянием `contextTab`, массивом `[key, label, count]` и функцией переключения контента — по образцу уже существующего паттерна `PersonDetailPage` (`resources.jsx:667-682`), а не CSS/разметки из `TaskDetailPage`.

Подвкладки: **Команда | Задачи | Проблемы | Ссылки | Заметки**, каждая со счётчиком.

- **Команда** — список участников проекта (аватар, имя, роль, текущий режим загрузки как подпись). Без контрола управления загрузкой в самом списке — управление только через кнопку в «Свойствах».
- **Задачи** — фильтр `!task.archivedAt && task.status !== 'done'` (тот же, что уже применяется в `PersonDetailPage` для `regularTasks`, `resources.jsx:643`), сортировка — существующей функцией `taskSort` (`pages/tasks.jsx:58`: статус → приоритет "важная" впереди → просроченные впереди → по сроку → по названию). `taskSort` и вспомогательный `orderIndex` сейчас не экспортируются из `tasks.jsx` — экспортировать их оттуда и импортировать в `resources.jsx`, без дублирования логики.
- **Проблемы** — фильтр `issue.status !== 'resolved'`.
- **Ссылки** — без изменений логики: тот же `task-relations-list`/форма добавления, что сейчас в секции "Внешние ссылки".
- **Заметки** — встроенный (не в боковой шторке) `StickyNotes` (`entityType="project"`, `entityId=project.id`), с кнопкой «Добавить стикер» в тулбаре вкладки и счётчиком через `onCountChange` (паттерн `workspace.jsx:284/391`).

Раздел «Цели» (связанные цели) с проектной страницы убирается полностью.

## Колонка «Свойства»

- **Статус** — иконка + текст, редактируется по клику. Новый компонент `ProjectStatusIcon` в `components/status.jsx`, по образцу `IssueStatusIcon`/`ProcessStatusIcon`: маппинг `active/paused/done` на существующие глифы `TaskStatusGlyph` (`active→in_progress`, `paused→paused`, `done→done`), через `useEntityStatus({resource:'projects', validValues:['active','paused','done'], fallback:'active'})`. Рядом с иконкой — текстовая подпись (`PROJECT_STATUS_LABEL[project.status]`), как в `task-property-row` "Статус" (`tasks.jsx:676`).
- **Ключ** — инлайн-редактируемое поле по клику: в режиме просмотра — текст ключа; клик превращает его в `<Input>` (uppercase, ≤4 символов `[A-Z0-9]`, автофокус); Enter/blur сохраняет через `api.resource('projects').update(id, {projectKey})`; Escape отменяет правку, возвращая исходное значение. Ошибки валидации/конфликта (400/409 "такой ключ уже используется") показываются инлайн под полем — переиспользуются формулировки из текущего `ProjectCrudDialog` (`resources.jsx:952`).
- **Кнопка «Управлять загрузкой»** — без изменений (`ProjectLoadDialog`), просто часть «Свойств».

## Меню «⋯»

По образцу `TaskDetailPage` (`tasks.jsx:614`): `DropdownMenu` с иконкой `MoreHorizontal`, пункты:
1. **Архивировать проект / Восстановить из архива** — `patch({archivedAt: project.archivedAt ? null : new Date().toISOString()})`, иконки `Archive`/`ArchiveRestore` из `lucide-react`.
2. **История версий** — открывает `VersionHistoryDialog` (`entityType="projects"`, `entityId=project.id`).
3. Разделитель (`DropdownMenuSeparator`), затем **Удалить** (`text-destructive`) — `confirm('Удалить проект?')` → `api.resource('projects').remove(id)` → `navigate('/projects')`.

`ProjectCrudDialog` в режиме редактирования (`isEdit`) становится недостижимым (имя/описание/статус — теперь инлайн, вызов с проектной страницы убирается). Убрать мёртвый код: `isEdit`-ветки в диалоге, кнопку и `AlertDialog` удаления внутри него, `status`-`Select`, всё что относится только к режиму правки существующего проекта. Диалог остаётся исключительно для создания нового проекта (вызов из `ProjectsPage`, `resources.jsx:552`, `project=null`).

## Архив проектов (бэкенд)

Чтобы «Архивировать проект» реально исключало проект из общих списков/расчётов (как у задач) и версионирование работало для истории:

- **`server/access-control.js:114-118`** (`visibleItems`) — расширить условие фильтрации архива: `if ((name === 'tasks' || name === 'projects') && !opts.includeArchived) items = items.filter((item) => !item.archivedAt);`. Это единая точка, через которую идут все обычные списки (`useResource('projects')` → `PersonLoadDialog`/`PersonLoadDialog`'s `activeProjects`, `TeamLoadPage`, `ProjectsPage`, мемо/автокомплиты с упоминаниями и т.д.) — архивные проекты пропадают из них без точечных правок каждого места.
- **`server/application/resource-service.js:25`** (`isVersioned`) — добавить `'projects'` в список версионируемых имён: `name === 'tasks' || name === 'meetings' || name === 'processes' || name === 'projects' || (name === 'labs' && item?.entityType !== 'idea')`. Сейчас проекты вообще не пишут версии — без этого `VersionHistoryDialog` на странице проекта будет всегда пустым.
- **`server/versioning.js`** — добавить в `LABELS`:
  ```js
  projects: {
    name: 'название', description: 'описание', projectKey: 'ключ', status: 'статус',
    memberIds: 'участников', memberLoads: 'загрузку', externalLinks: 'ссылки', archivedAt: 'архив',
  },
  ```
  в `creationSummary` — ветку `if (entityType === 'projects') return 'Создан проект';`;
  в `isImportantChange` — ветку `if (entityType === 'projects') return fields.has('status') || fields.has('archivedAt');`.

Прямая загрузка проекта по `id`/`projectKey` (`get()` в `resource-service.js`) архив не фильтрует — со страницы архивного проекта всегда можно зайти по прямой ссылке и восстановить его через меню «⋯», как и с задачами.

## Что не меняется

- Модель данных проекта — без изменений, кроме нового поля `archivedAt`.
- Эндпоинт `/api/projects/:id/detail` — набор полей ответа не меняется (`project, tasks, members, issues`; `goals` в ответе может остаться на сервере, просто не используется на фронте, как и раньше `journal`/`meetings`/`agreements`).
- `ProjectLoadDialog`, `PersonLoadDialog`, `TeamLoadPage`, `lib/domain.js` (`PROJECT_LOAD_OPTIONS`, `normalizeProjectMemberLoad`, `personProjectLoadSummary`) — без изменений в логике, кроме автоматического исключения архивных проектов через `visibleItems`.
- Стилистика `task-relations-list`/`task-relations-empty` для ссылок — переиспользуется как есть.

## Проверка

- Ручная проверка в браузере: переключение вкладок/подвкладок с сохранением состояния при `reload()`; инлайн-правка названия/описания/статуса/ключа (успех и ошибка конфликта ключа); архивирование → проект пропадает из `ProjectsPage`, `TeamLoadPage`, пикеров проекта у задач/встреч, но открывается по прямой ссылке и восстанавливается; история версий показывает записи после нескольких правок; удаление проекта уводит на список проектов.
- Не заводится отдельный набор автотестов — проект не имеет тестовой инфраструктуры для UI (сверить с существующей практикой репозитория перед реализацией).
